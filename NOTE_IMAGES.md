# Screenshots in Notes

Open or create a note, then paste a screenshot with Ctrl+V/Cmd+V or use **+ Image**. Plain-text paste remains native. Images appear in the Screenshots section above the writing canvas; newly added images scroll into view automatically. **Copy image** writes a PNG to the clipboard where supported; **Remove image** captures a recovery copy before removing the note reference.

Image-only pages are saved. References participate in normal note normalization, signatures, live open-note merging, account saves, and backup snapshots. The binary content is stored separately at `users/{uid}/noteImages/{sha256}` through `note-images.js`, using the existing owner-only `/users/{uid}/...` rule. Writes must finish before an image reference is inserted. Upload/read operations capture and recheck the account identity. Assets are validated and SHA-256 checked on read/import; browser cache is cleared on authentication changes.

## Writing on screenshots

In Edit, the screenshots sit inside the drawing surface, above the paper. **Pen** and **Eraser** work on each screenshot and in the blank space beside it, and in **Type** mode a click on a screenshot (or beside it) places a text box there, in either typing mode. Ink on a screenshot gets a thin dark halo and its text boxes a dark chip, so both read on bright and dark images. Undo/Redo, the page's ink limits, saving, live merging and the save-size check are the same as for the paper. Read view shows the marks too, but they can't be edited there. **Copy image** copies the picture without the marks. **Remove image** also removes its marks (the recovery copy taken first keeps them).

A mark is an ordinary stroke or text box carrying the screenshot's `imageId`. Its x/y are pixels from the image's top-left corner, measured while the image was shown `pageWidth` pixels wide, so marks scale with the image when the window resizes and stay put when the page scrolls. When marks reach past the image's right edge, the image is shown narrower so they still fit in its row (the PDF does the same). In the saved account, marks live in their own `noteImageMarks` map (`{ [noteId]: { drawing, textBoxes } }`, ink packed like other handwriting), not in `noteDrawings` / `noteTextBoxes`. An older cached app version doesn't know that map and passes it through untouched, so it can't drop or misplace the marks. Loading puts the marks back on their page and drops marks whose screenshot is no longer on it. The PDF draws each screenshot with its marks. Tests: `tests/note-image-marks.test.cjs`.

Supported inputs: PNG, JPEG, WebP, and GIF (a still frame), up to 20 MB and 50 million decoded pixels. Images are resized to at most 2400 pixels on the longest edge and compressed to a maximum 800,000-character raster data URL, below the Firestore document limit. Source files are not retained at original resolution. This avoids placing image bytes in the main workspace blob, which has its own 900,000-byte limit.

Version 3 JSON backup downloads include all referenced screenshot assets and an additional checksum. Import verifies every referenced asset before restoring; assets are uploaded into the destination account before the notes are replaced. Older image-free backups remain supported. Cloud recovery copies reference the immutable image documents: images are intentionally retained when removed from a note, so older snapshots can still display them. This retention can increase stored data over time. The previously identified whole-workspace sync races and lack of managed disaster recovery are separate unresolved issues; this feature does not claim to fix them.

Verification: account scoping, changed-owner rejection, failed writes, corrupt asset reads, new-session loading, and cross-account backup import are tested with a simulated Firestore adapter. Browser checks use isolated synthetic accounts/storage: clipboard paste, file upload, Copy image followed by actual Ctrl+V, image-only saves, and reopening after reload. Real production-account image writes were not performed as part of these tests.
